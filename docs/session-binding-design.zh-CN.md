# 会话绑定与自动恢复流程设计

状态：rc.8 已按下述设计实现持久目录、双端接受、定向组路由、暂停恢复和动态接收器。
实际操作及当前限制以 [会话使用说明](sessions.zh-CN.md) 为准；验收记录单独记录真实机器结果。

## 目标

用户在一个新聊天中说“使用 agent-link，与 home-ds-dev 协作”，系统应完成
当前聊天注册、选择对端、绑定通信范围及本机唤醒定位。用户不需要抄写
worker session、原生聊天 ID、设备 ID，不需要逐个编辑 JSON/YAML 或重启应用。

**绑定跟着原生聊天走，不跟进程、窗口标题或可读名称走。** 同一个聊天重新
打开时自动恢复；新建聊天产生独立身份。一个聊天加入多个协作组，多个聊天
加入同一个协作组，以此支持一对一、一对多和多对多。

首次安装宿主接入仍可能需要一次重载。后续注册、加入/退出协作组和修改接收
范围应动态生效；不能把“首次加载插件”和“日常会话绑定”混成每次重启操作。

## 身份和绑定关系

| 对象 | 含义 | 生命周期 |
| --- | --- | --- |
| 设备 | 现有 office-mac、home-mac 及其配对身份 | 沿用已有身份和配对 |
| 会话端点 | 一个真实宿主聊天，对应一个保留的 worker session | 同一个原生聊天重开可恢复 |
| 显示名称 | 如 office-codex、home-ds-dev、home-ds-review | 方便选择，可以改名；不决定路由 |
| 协作组 | 如 starx-dev，保存成员和通信/唤醒范围 | 独立于某次应用启动 |

每个本地端点保存设备、宿主类型/配置实例、真实原生聊天 ID、保留的 worker、
显示名称、接收开关及本机适配器状态。未命名时使用“设备-宿主-首次注册月日-时分-端点短码”，按北京时间生成后保持稳定。原生聊天 ID 只留在接收机器，远端只需要
端点地址。实际 native owner 在连接/提交时重新核验，不长期保存一个进程 PID
作为聊天身份。

当前聊天重开时，按“设备 + 宿主配置实例 + 原生聊天 ID”查找旧端点，复用原
worker；新聊天创建新 worker。同一个聊天显示在两个窗口时仍是同一个逻辑
端点，并且只允许一个有效监听。重复注册是幂等操作，不产生重复接收器。

同一机器两个不同 DeepSeek 聊天可命名为 home-ds-dev、home-ds-review。如果
用户只说 home-ds 而存在多个候选，应列出候选让用户选择一次，不能自动选
“最近活跃”的窗口，也不能把新聊天接替到旧聊天的名称、任务租约或历史上。

## 固定操作流程

### 1. 首次使用：自动注册当前聊天

不是扫描所有聊天。只在用户请求使用 agent-link，或其明确启用的宿主启动
集成运行时，为当前聊天执行注册/恢复。

1. 宿主适配器获取当前聊天的真实上下文，并验证其原生 ID/owner。
2. daemon 查找已有端点：找到则恢复；没有则创建并保存唯一 worker。
3. CLI 与 MCP 返回同一个端点，后续发送、收件和租约使用它。
4. 本机确认接收器已关联此端点；未支持原生唤醒的宿主只能显示手动接收。

Codex/DeepSeek 的已知原生上下文可用于自动识别。共享 MCP 进程不等于共享
聊天上下文：无法可靠识别调用者时，必须由宿主传递上下文或通过当前聊天的
shell 环境完成注册，不能退回 MCP 进程默认 session 或拿别的聊天代替。

CLI：

```sh
agent-link session attach --name office-codex
agent-link session list
```

native ID 从本地宿主上下文获得，不要求用户手填。`attach` 返回稳定的本地
端点引用；MCP 进程重启后也能通过这次 attach 恢复该聊天的原 worker，而非
只信任本进程临时生成的 sessions 集合。会话引用仍是路由上下文，不是权限隔离。

### 2. 选择协作组和对端

用户可以直接说：

> 把当前聊天命名为 office-codex，加入 starx-dev，与 home-ds-dev 协作并启用收件唤醒。

系统只从已配对设备查询已注册端点。候选展示设备、宿主、名称、简短端点标识
和实际接收状态。第一次选择后把具体端点保存到组成员中，后续不按名字猜测。

CLI：

```sh
agent-link bind home-ds-dev --channel starx-dev
agent-link bind home-ds-dev home-codex --channel starx-dev
agent-link bindings
```

发起方提出绑定，接收方登记其本地接收范围。已有明确授权的协作规则可以自动
接纳；首次加入尚未授权的组，由接收端在对应聊天中说“加入 starx-dev”完成。
**不能靠一次远端请求，为未选择的聊天自动打开接收。** 未注册的聊天也无法
凭名字被凭空唤醒：必须先在那个聊天完成一次注册，之后才有可恢复的地址。

设备初次配对仍复用现有流程，已经配对的设备不因新聊天注册而重复配对。
无需为每两个聊天分别创建一套会话绑定；实际跨设备发送仍要求设备之间已配对，
不能通过组成员传递设备信任。接收端保存自己接受的成员/范围；新成员变化按
该端已有组规则处理，远端不能单方面扩大它的接收范围。

### 3. 绑定成功：分别显示接通和验证结果

用户看到的结果应类似：

```text
当前聊天：office-codex @ office-mac
协作组：starx-dev
对端：home-ds-dev @ home-mac
通信绑定：已完成
原生接收器：已连接
模型唤醒：待空闲验证 / 已验证（上次成功时间）
```

绑定握手、目录同步和心跳由 daemon/适配器完成，不消耗模型回合。首次启用
一个新的接收端点/适配器版本时，排队执行一次非秘密唤醒探针；只有真实新
模型回合回传正确探针结果后才显示“模型唤醒已验证”。普通重新连接不重复做
整套模型测试，保留上次验证时间；新的真实失败应更新状态。

当前模型还在注册/绑定回合中时，探针等待其结束；绑定命令先返回“已绑定，
待空闲验证”。不用人类再次输入“继续”才能验收。native ACK、可见提示气泡
或 daemon 在线都不能单独算作模型成功，rc.6 的失败是必须覆盖的回归案例。

### 4. 正常通信：点名接收者

```sh
agent-link send --channel starx-dev --to home-ds-dev --text "检查当前 dev 环境状态"
```

这是友好地址解析；底层仍投递到精确设备和 `to_session`。原命令的
设备寻址形式继续保留。只有一个唯一对端的直接会话，可以由绑定上下文补齐
接收者；存在多个对端时要求点名，不把无接收者的消息默认为群发。

接收链路固定为：

```text
协作组 + 具体接收端点
  → 对端 daemon 保存消息
  → 核对来源端点、组成员及本机接收开关
  → 查找本地端点的真实原生聊天
  → 空闲时通知；忙碌/审批时排队；暂不可用时保留
```

自动唤醒必须同时匹配来源设备、来源 worker、接收端点和协作组；只有设备级
allowlist 不足以区分 home-ds 与同机 home-codex。原生 ID 不从远端消息读取。

task/result 默认沿用定向唤醒；绑定时可以明确开启“聊天文本也唤醒”，只用于
被点名的会话。文件仍受现有 MCP 文件权限限制。绑定元数据、心跳、进度、
收件回执不唤醒，普通组公告默认只保存，防止接收器之间自动确认形成循环。

### 5. 重开、暂停和解绑

| 情况 | 行为 |
| --- | --- |
| 同一个聊天重新打开 | 自动 attach 回原端点、恢复已接受的组，不手填配置 |
| 新建聊天 | 新端点；可选择加入已有组，不自动冒用旧名称和租约 |
| 只是切换/最小化窗口 | 不据此推断模型停止；以原生状态为准 |
| 宿主退出或原生 owner 不可用 | 显示暂不可唤醒；消息/队列保留，连接恢复后继续 |
| 模型网络出错 | 显示已绑定但模型不可用，不能把 daemon 在线当作模型在线 |
| 用户暂停接收 | 持久保存暂停状态；应用重开不擅自恢复 |
| 离开一个协作组 | 停止该组的新唤醒，不影响其他组及历史 |

CLI：

```sh
agent-link session pause
agent-link session resume
agent-link unbind --channel starx-dev
```

暂停/离组不自动取消正在执行的业务任务，不转移任务租约，也不丢弃已收到的
消息。已开始任务的结果返回仍需能交付原发起端点：作为原请求的关联回复处理，
不可因别名改名或普通离组而投递到另一个聊天。离组后这类历史回复是否通知，
按明确的本机暂停策略执行，不重新开放该组的新任务接收。

## 一对多、多对多的规则

```text
starx-dev 成员：
  office-codex
  home-ds-dev
  home-codex

office-codex → home-ds-dev            仅 DS 收到定向唤醒
office-codex → home-ds-dev,home-codex 两份独立投递
home-ds-dev → home-codex             同组成员可直接定向通信
```

“同组”代表可建立通信关系，不代表每条消息都抄送全组。组内回复默认返回原
发送端点，不自动广播。显式群发采用成员端点快照，成员后来加入不会补领旧
任务。群发任务按接收者生成独立 message/task ID、独立租约和独立结果；不能
让多人争抢一个任务 ID，再把第一个完成当作全组完成。发送失败逐个报告。

同一个聊天可加入 starx-dev、代码审查等多个组；组之间不自动转发。名称不
唯一时显示候选，不静默转给某个最近上线的端点。组创建、成员变更和邀请本身
不能授权部署、执行任意命令、传送凭据或提升 MCP 权限。

## 最小实现范围

复用现有 daemon、SQLite、加密消息、local/LAN/cloud 自动路由、任务租约和
唤醒队列，不加新的公网服务、独立账户体系、消息总线或全功能群聊界面。

1. daemon 增加持久化会话目录、协作组和已接受的成员关系；本机保存原生映射。
2. CLI/MCP 共用 attach/list/bind/unbind/status 的本地 API，友好名称统一解析。
   MCP 从 daemon 恢复当前已验证聊天的 worker，不依赖一个全局进程默认值。
3. 宿主接入初装一次，之后监听本机目录变化。DeepSeek 的已加载插件动态管理
   多个真实聊天；Codex 可先自动管理现有每聊天 sidecar，不要求先合并成一个
   新的全局服务。底层监听/状态锁继续保持每聊天独立。
4. 新绑定自动生成/更新本机唤醒参数，动态调整成员和组过滤，不再要求逐聊天
   编辑 Cordis patch 或手写 LaunchAgent。普通绑定变更不重启应用或 daemon。
5. 远端目录和组握手复用现有已配对加密通道；只传逻辑地址，不传原生聊天 ID、
   本地路径、凭据或聊天正文。首版可用现有 progress 信封承载严格校验的 v1
   元数据控制体，保留现有协议字段和签名形式；不把它当模型任务，不添加
   远端执行操作。旧端只会保存普通进度且不会触发唤醒；没有能力握手回包时
   明确报告不支持并退回旧寻址，不持续重复探测。兼容性必须做混合版本测试，
   不能把普通送达回执当作支持新绑定的证明。

新 `--channel` 将稳定频道 ID 写入现有 conversation 字段，名称仅作选择和
展示，任务仍靠独立 ID/reply_to 跟踪。旧 `--conversation` 的语义保持不变；
两种参数不能混用，已有按任务 conversation 的调用只在显式迁移后切换。
会话目录只是一份已注册端点目录，不是全机聊天目录，也不伪造模型活跃心跳。

现有每个 macOS 用户共享 daemon、历史和缓存的边界不变；这些绑定提供路由、
接收范围和防误投，不能宣称同用户不同模型之间实现了权限或文件访问隔离。

## 迁移与验收

先导入现有真实 native ID/worker 映射并标明旧绑定范围，不重新创建身份、
不清空队列、历史或租约。当前 office/home 的已验收绑定继续工作。只有双方
升级并接受新协作组后才切换到新流程，保留旧 CLI/MCP 的手动寻址入口。

按以下顺序实现和联调，不一次加入角色自动接班、跨组转发等能力：

1. 当前 office-codex/home-ds 的注册、绑定和重开恢复：不用复制 ID、不重启
   桌面应用，且复用原 worker。
2. 同机两个不同 home-ds 聊天：独立端点；各自定向、各自唤醒，没有抢任务或
   唤醒错聊天。重复 attach 不启动重复监听。
3. 同一协作组的一对多、多对多：独立任务 ID、正确回传、部分离线不误报全组
   成功；同一聊天加入两个组后不发生自动转发。
4. 原生 owner 变化、MCP 重启、宿主退出重开、忙碌/审批、显式暂停、离组、旧
   客户端及不确定提交恢复。验证不自动接替新聊天、不丢消息、不重复执行。

每一步分开记录“已绑定、消息送达、原生接纳、真实模型完成”，只有真实模型
证据匹配具体端点时才通过唤醒验收。home-codex 的模型网络未恢复前，仍不能
把服务在线或绑定成功计作它的模型联调通过。

[会话绑定验收](session-binding-verification.zh-CN.md)，其中另记后续真实
home-codex 接入和双向原生模型唤醒，不用上述待验计划代替完成证据。
